# KPI Design For Managers And Designers

## Goal

Добавить в локальную CRM помесячный KPI для сотрудников ролей `manager` и `designer`.

Система должна позволять:
- хранить KPI как отдельные записи по месяцам;
- задавать KPI только директору;
- показывать KPI на отдельной странице сотрудника;
- поддерживать разные метрики для разных ролей;
- в первом этапе хранить и редактировать только плановые показатели;
- во втором этапе без перелома модели добавить фактические значения и процент выполнения.

## Scope

Входит в текущий этап:
- новая роль `designer`;
- новая сущность `monthly_kpis` в локальной базе;
- переход со страницы сотрудников на отдельную KPI-страницу сотрудника;
- создание и редактирование KPI по месяцам;
- история KPI по месяцам;
- доступ только для директора.

Не входит в текущий этап:
- автоматический расчёт факта;
- бонусы, штрафы и зарплатные расчёты;
- конструктор произвольных KPI;
- массовое редактирование KPI по нескольким сотрудникам сразу.

## Recommended Product Model

### Why monthly records

KPI должен храниться не у профиля сотрудника, а в отдельной таблице, потому что:
- показатели меняются от месяца к месяцу;
- нужна история;
- позднее понадобится сравнение плана и факта;
- одна запись на сотрудника не решает задачу динамики и отчётности.

### Why a dedicated KPI page

Редактирование KPI прямо в таблице сотрудников не подходит, потому что:
- таблица сотрудников должна оставаться компактной;
- KPI быстро разрастается по полям и месяцам;
- отдельная страница позволяет показать историю, форму редактирования и затем аналитику выполнения;
- это проще расширять без деградации основного списка сотрудников.

## Roles And Permissions

### Supported roles

Система после изменения поддерживает 4 роли:
- `director`
- `financier`
- `manager`
- `designer`

### Access rules

`director`
- видит страницу сотрудников;
- видит KPI-страницы сотрудников;
- может создавать и редактировать KPI;
- может создавать и редактировать пользователей с ролями `manager`, `designer`, `financier`, `director`.

`manager`
- не видит и не редактирует KPI сотрудников;
- работает как сейчас по своим заказам.

`designer`
- на первом этапе существует как роль сотрудника;
- не получает отдельный рабочий кабинет;
- не видит и не редактирует KPI сотрудников.

`financier`
- не управляет KPI сотрудников.

## Data Model

### Profile role

Тип `UserRole` расширяется новым значением:
- `designer`

### New entity: monthly_kpis

Добавляется новая сущность `monthly_kpis`.

Одна запись = один сотрудник + один месяц.

Поля:
- `id: string`
- `user_id: string`
- `month: string`
- `role: 'manager' | 'designer'`
- `sales_plan: number | null`
- `orders_plan: number | null`
- `new_clients_plan: number | null`
- `tasks_plan: number | null`
- `on_time_rate_plan: number | null`
- `revision_limit_plan: number | null`
- `created_at: string`
- `updated_at: string`

### Month format

Поле `month` хранится в формате `YYYY-MM`, например:
- `2026-05`
- `2026-06`

Это упрощает:
- фильтрацию;
- сортировку;
- уникальность записи;
- локальную сериализацию.

### Logical uniqueness

В локальной БД должен соблюдаться логический инвариант:
- для одной пары `user_id + month` может существовать только одна KPI-запись.

При повторном сохранении для того же месяца запись обновляется, а не дублируется.

### Role-specific fields

Для `manager` используются:
- `sales_plan`
- `orders_plan`
- `new_clients_plan`

Для `designer` используются:
- `tasks_plan`
- `on_time_rate_plan`
- `revision_limit_plan`

Неиспользуемые для роли поля сохраняются как `null`.

## KPI Definitions

### Manager KPI

`sales_plan`
- месячный план продаж в деньгах.

`orders_plan`
- план по количеству заказов за месяц.

`new_clients_plan`
- план по количеству новых клиентов за месяц.

### Designer KPI

`tasks_plan`
- план по количеству выполненных задач или макетов за месяц.

`on_time_rate_plan`
- целевой процент задач, закрытых в срок.

`revision_limit_plan`
- допустимое среднее число правок на задачу.

## UI Design

## Users list page

Страница сотрудников сохраняет компактный вид.

Изменения:
- роль `designer` появляется в форме создания и редактирования сотрудника;
- для сотрудников ролей `manager` и `designer` появляется действие `KPI`;
- действие ведёт на страницу `/users/:id/kpi`;
- для ролей `director` и `financier` действие `KPI` не показывается.

## KPI page

Новый маршрут:
- `/users/:id/kpi`

Страница состоит из 3 блоков.

### 1. Header and employee card

Показывает:
- имя сотрудника;
- роль;
- логин;
- статус активности;
- кнопку возврата к списку сотрудников.

### 2. KPI editor

Показывает:
- выбор месяца;
- форму KPI по роли;
- кнопку `Сохранить`.

Поведение:
- если запись за выбранный месяц уже есть, форма загружается из неё;
- если записи нет, открывается пустая форма с нулями или пустыми значениями;
- директор может сохранить запись;
- остальные роли страницу открыть не могут.

### 3. KPI history

Таблица истории KPI по месяцам:
- месяц;
- ключевые показатели по роли;
- дата обновления;
- действие `Редактировать`.

Сортировка:
- от нового месяца к старому.

## Validation Rules

### General

- месяц обязателен;
- сотрудник должен существовать;
- KPI можно ставить только сотруднику ролей `manager` и `designer`;
- KPI для директора, финансиста и других ролей создавать нельзя.

### Numeric rules

Для всех числовых KPI:
- значение должно быть числом;
- отрицательные значения запрещены.

Дополнительно:
- `on_time_rate_plan` должен быть в диапазоне от `0` до `100`;
- `revision_limit_plan` допускает дробные значения;
- денежные поля хранятся числом и редактируются через price input.

## Local Database Changes

Нужно расширить локальную модель:
- тип таблиц;
- интерфейс `LocalDatabaseState`;
- вставку и обновление `monthly_kpis`;
- materialize/select слой;
- import/export/reset local data.

Seed data:
- можно добавить 1-2 демо KPI-записи для менеджера;
- для дизайнера допустимо оставить пустую историю.

## Routing And Guards

Нужны изменения:
- новый route `/users/:id/kpi`;
- guard только для `director`;
- если сотрудник не найден, показывать стандартное состояние `not found`;
- если роль сотрудника не поддерживает KPI, показывать понятное сообщение, а не пустую страницу.

## Error Handling

Нужно явно обработать:
- сотрудник не найден;
- попытка открыть KPI для неподдерживаемой роли;
- сохранение KPI с некорректным месяцем;
- попытка создать дубликат записи за тот же месяц;
- ошибка импорта старого local snapshot без `monthly_kpis`.

## Testing Strategy

### Unit

Добавить unit-тесты на:
- нормализацию месяца;
- выбор метрик по роли;
- upsert-поведение `user_id + month`;
- валидацию KPI.

### Browser smoke

Добавить сценарий:
- логин под директором;
- переход в сотрудников;
- создание или открытие сотрудника с ролью `designer`;
- переход на KPI-страницу;
- сохранение KPI за месяц;
- повторное открытие страницы и проверка, что запись сохранилась.

## Implementation Order

1. Расширить типы ролью `designer`.
2. Расширить local DB новой сущностью `monthly_kpis`.
3. Добавить операции чтения и upsert для KPI.
4. Обновить форму пользователя и список сотрудников.
5. Создать KPI-страницу сотрудника.
6. Добавить route и guards.
7. Добавить unit и browser tests.

## Future Extension Path

Модель должна позволить без миграционного перелома добавить:
- фактические KPI;
- процент выполнения;
- статус `выполнен / риск / не выполнен`;
- аналитику KPI по сотрудникам;
- бонусный модуль.

Рекомендуемое расширение на втором этапе:
- добавить фактические поля в отдельный derived calculation слой, а не в первичную форму ввода;
- сначала считать факт для `manager` из заказов и клиентов;
- для `designer` факт добавлять только после появления полноценного модуля задач.

## Final Decision

В проект внедряется модель:
- отдельная KPI-страница сотрудника;
- отдельная сущность `monthly_kpis`;
- новая роль `designer`;
- KPI по месяцам только для `manager` и `designer`;
- создание и изменение KPI только директором;
- на первом этапе сохраняется только план.
