# Order Tickets Design

## Goal

Добавить в CRM рабочий тикет внутри заказа для передачи задачи менеджеру и дизайнеру.

Система должна позволять:
- иметь один тикет на один заказ;
- назначать в тикете две роли: `manager` и `designer`;
- использовать один общий статус тикета:
  - `new`
  - `in_progress`
  - `done`
- создавать тикет только внутри заказа;
- давать управление тикетом ролям `director` и `manager`;
- давать дизайнеру рабочий список назначенных ему тикетов.

## Scope

Входит в первый этап:
- новая роль `designer` как полноценный участник workflow;
- новая сущность `order_tickets`;
- один тикет на заказ;
- создание тикета из карточки заказа;
- список тикетов;
- детальная страница тикета;
- доступы по ролям;
- базовая история и поля назначения.

Не входит в первый этап:
- несколько тикетов на один заказ;
- комментарии внутри тикета;
- вложения;
- чеклисты;
- отдельные статусы по каждой роли;
- SLA и уведомления;
- автоматическое создание тикета при каждом заказе.

## Product Model

### Main rule

Один заказ может иметь не более одного production-ticket.

Заказ остаётся основной бизнес-сущностью, а тикет является рабочим операционным слоем внутри него.

### Why ticket is separate from order

Тикет не должен храниться набором полей прямо в `orders`, потому что:
- у него свой lifecycle;
- у него свои исполнители;
- позже у него почти наверняка появятся история, комментарии, вложения и сервисные поля;
- отдельная сущность проще расширяется без загрязнения модели заказа.

### Ticket status model

У тикета один общий статус:
- `new`
- `in_progress`
- `done`

Это означает:
- статус меняется для всего тикета целиком;
- менеджер и дизайнер не имеют отдельных подстатусов;
- если один участник закончил раньше другого, это не отражается отдельным статусом на первом этапе.

Такой подход выбран потому что он проще в работе, понятнее для директора и не перегружает интерфейс.

## Roles And Permissions

### Supported roles

Система поддерживает роли:
- `director`
- `financier`
- `manager`
- `designer`

### Ticket permissions

`director`
- видит все тикеты;
- создаёт тикеты;
- редактирует тикеты;
- меняет статус;
- меняет обоих исполнителей.

`manager`
- видит тикеты только своих заказов;
- создаёт тикет внутри своего заказа;
- редактирует тикет внутри своего заказа;
- назначает дизайнера;
- меняет общий статус тикета.

`designer`
- видит только тикеты, где он назначен;
- открывает детальную страницу тикета;
- меняет общий статус тикета;
- не создаёт тикет;
- не меняет менеджера и дизайнера.

`financier`
- не участвует в тикетах;
- не видит раздел тикетов.

## Data Model

### New enums

Добавить:
- `OrderTicketStatus = 'new' | 'in_progress' | 'done'`

### New entity: order_tickets

Поля:
- `id: string`
- `order_id: string`
- `title: string`
- `description: string | null`
- `status: OrderTicketStatus`
- `manager_assignee_id: string`
- `designer_assignee_id: string`
- `deadline: string | null`
- `created_by: string`
- `created_at: string`
- `updated_at: string`

### Data invariants

- один `order_id` -> максимум один тикет;
- тикет не существует без заказа;
- `manager_assignee_id` должен ссылаться на пользователя с ролью `manager`;
- `designer_assignee_id` должен ссылаться на пользователя с ролью `designer`;
- статус по умолчанию `new`;
- при создании тикета `created_by` обязателен.

## UX Flow

### Recommended creation flow

1. Менеджер или директор открывает карточку заказа.
2. В блоке `Тикет производства` нажимает `Создать тикет`.
3. Форма автоматически подставляет:
   - `title` из названия заказа;
   - `description` из описания заказа;
   - `manager_assignee_id` из менеджера заказа;
   - `deadline` из дедлайна заказа.
4. Пользователь выбирает дизайнера.
5. Сохраняет тикет.
6. Тикет сразу появляется:
   - в заказе;
   - в разделе `Тикеты` у директора;
   - в разделе `Тикеты` у назначенного дизайнера;
   - в разделе `Тикеты` у менеджера, если заказ его.

### Why this flow is preferred

- нет двойного ввода;
- заказ остаётся первичным объектом;
- менеджеру не нужно сначала идти в отдельный модуль;
- дизайнер получает готовый список работы без доступа к лишним частям CRM.

## Screens

## 1. Order detail page

В карточке заказа появляется отдельный блок `Тикет производства`.

Если тикета нет:
- кнопка `Создать тикет`.

Если тикет есть:
- статус;
- менеджер;
- дизайнер;
- дедлайн;
- описание;
- кнопка перехода в тикет.

## 2. Tickets list page

Новый раздел меню: `Тикеты`.

Страница показывает:
- список тикетов;
- статус;
- заказ;
- клиент;
- менеджер;
- дизайнер;
- дедлайн.

Фильтры первого этапа:
- `все`
- `новые`
- `в работе`
- `готово`
- `мои`

Где `мои` означает:
- для директора: все;
- для менеджера: тикеты его заказов;
- для дизайнера: тикеты, где он назначен.

## 3. Ticket detail page

Отдельная страница тикета:
- шапка с номером заказа и клиентом;
- статус;
- дедлайн;
- блок назначений;
- описание;
- действия по изменению статуса и назначений по правам.

## Routing

Новые маршруты:
- `/tickets`
- `/tickets/:id`

Карточка заказа должна ссылаться на `/tickets/:id`.

## Local Database Changes

Нужно расширить local DB:
- добавить таблицу `order_tickets`;
- добавить seed для минимум одного дизайнера;
- добавить чтение списка тикетов;
- добавить чтение одного тикета;
- добавить создание тикета;
- добавить обновление тикета;
- добавить import/export/reset/migration поддержку.

## Hooks

Новые hooks:
- `useOrderTickets`
- `useOrderTicket`

Изменить:
- `useOrder`

Цель:
- карточка заказа должна знать про свой тикет;
- список тикетов должен фильтроваться по роли текущего пользователя;
- дизайнер не должен видеть чужие тикеты;
- менеджер не должен видеть тикеты чужих заказов.

## Validation Rules

- нельзя создать тикет без `order_id`;
- нельзя создать второй тикет для того же заказа;
- title обязателен;
- manager обязателен;
- designer обязателен;
- статус должен быть одним из `new | in_progress | done`;
- дизайнер должен реально иметь роль `designer`;
- менеджер должен реально иметь роль `manager`.

## Access Rules In UI

На уровне интерфейса:
- `director` видит меню `Тикеты`;
- `manager` видит меню `Тикеты`;
- `designer` видит меню `Тикеты`;
- `financier` не видит меню `Тикеты`.

В карточке заказа:
- `director` и `manager` видят `Создать тикет` и действия редактирования;
- `designer` может открыть тикет только если он назначен;
- `financier` не работает с тикетами.

## Minimal First Release

Первый релиз должен включать только:
- сущность `order_tickets`;
- один тикет на заказ;
- назначение менеджера и дизайнера;
- общий статус;
- список тикетов;
- детальную страницу;
- создание тикета из заказа.

Нельзя перегружать первый релиз дополнительными сущностями.

## Testing Strategy

### Unit

Проверить:
- валидацию статусов;
- валидацию ролей исполнителей;
- невозможность второго тикета для того же заказа.

### Browser smoke

Проверить сценарий:
1. логин под директором;
2. создание дизайнера;
3. открытие существующего заказа;
4. создание тикета внутри заказа;
5. назначение менеджера и дизайнера;
6. переход в список тикетов;
7. логин под дизайнером;
8. проверка, что дизайнер видит только свой тикет;
9. смена статуса на `in_progress`;
10. смена статуса на `done`.

## Future Extension Path

После первого релиза можно без смены модели добавить:
- комментарии;
- историю изменений;
- вложения;
- несколько тикетов на заказ;
- раздельные этапы по ролям;
- SLA;
- уведомления;
- KPI дизайнера на основе закрытых тикетов.

## Final Decision

В проект внедряется модель:
- тикет хранится как отдельная сущность `order_tickets`;
- тикет создаётся только внутри заказа;
- у заказа максимум один тикет;
- у тикета два исполнителя: `manager` и `designer`;
- у тикета один общий статус `new -> in_progress -> done`;
- тикетами управляют `director` и `manager`;
- `designer` работает через назначенные ему тикеты;
- первый релиз минимальный, без подзадач, комментариев и вложений.
