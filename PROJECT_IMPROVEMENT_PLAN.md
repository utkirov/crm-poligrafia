# CRM Poligraf Improvement Plan

_Актуально для состояния репозитория на 2026-05-04._

## Цель документа

Этот документ нужен как единый рабочий план по стабилизации, исправлению и развитию проекта `new-crm-polig`.

По нему можно:

- планировать спринты;
- брать задачи в работу по приоритету;
- проверять, что уже исправлено;
- не начинать новые фичи раньше, чем закрыты опасные места.

## Текущее состояние

На момент анализа:

- проект собирается через `npm run build`;
- `npm run lint` не проходит;
- в проекте есть критические риски вокруг денег, кэшбэка и составных операций;
- в коде много `supabase as any`, что сильно ослабляет TypeScript;
- часть UI-строк и PDF содержит проблемы с кодировкой;
- в репозитории не хватает эксплуатационной базы: полноценного README, CI, тестов, backend-контрактов и схемы Supabase.

## Главные проблемы

### P0. Критические

1. Двойное начисление кэшбэка возможно в двух разных местах:
   - `src/pages/OrderDetailPage.tsx`
   - `src/pages/PaymentsPage.tsx`
2. Создание заказа и денежные операции не атомарны:
   - `src/pages/OrderCreatePage.tsx`
   - `src/pages/OrderDetailPage.tsx`
   - `src/pages/PaymentsPage.tsx`
3. Логика важных бизнес-операций живет во фронтенде, а не в backend.
4. Нет гарантированной защиты от повторного запуска операций.

### P1. Высокий приоритет

1. `lint` красный из-за системных проблем с React Hooks и типизацией.
2. Supabase клиент не типизирован:
   - `src/lib/supabase.ts`
3. Роль `manager` объявлена, но не доведена до полноценного сценария доступа.
4. В коде есть битые символы и проблемы с локализацией:
   - `src/pages/OrderDetailPage.tsx`
   - `src/pages/UsersPage.tsx`
   - `src/components/GlobalSearch.tsx`
   - `src/utils/pdf.ts`

### P2. Средний приоритет

1. Тяжелые страницы и лишний вес бандла.
2. Слабая структура data layer.
3. Отсутствие тестов и CI.
4. Недостаточная документация по запуску и backend-части.

### P3. Улучшения

1. Улучшение UX.
2. Новые роли и рабочие сценарии.
3. Расширенная аналитика.
4. Напоминания и уведомления.

## Правила выполнения

Перед началом любых новых продуктовых фич соблюдать такой порядок:

1. Сначала закрыть P0.
2. Потом привести проект к зеленому `lint`.
3. Потом включить типизацию данных и тесты.
4. И только после этого активно расширять продукт.

Дополнительные правила:

- Не добавлять новые денежные сценарии до выноса бизнес-операций в backend.
- Не размножать новые `any`.
- Не делать новые крупные экраны поверх старого data layer, если еще не стабилизирован доступ к данным.
- Все критичные права доступа проверять не только в UI, но и в backend.

## Целевое состояние проекта

После выполнения плана проект должен:

- безопасно создавать, отменять, завершать и оплачивать заказы;
- исключать двойное начисление кэшбэка;
- иметь typed Supabase client;
- иметь зеленые `build`, `lint`, `test`;
- иметь понятные роли и матрицу доступа;
- иметь документацию по запуску и сопровождению;
- иметь базовые автотесты на ключевую бизнес-логику;
- быть удобным для дальнейшего масштабирования.

## Этап 2. Перенести критичную бизнес-логику в backend

### Цель

Убрать опасные составные операции из UI и сделать их атомарными.

### Что выносить в первую очередь

1. Создание заказа.
2. Завершение заказа.
3. Отмена заказа.
4. Проведение оплаты.
5. Изменение статуса заказа.
6. Создание/обновление пользователя.

### Рекомендуемый формат

Использовать один из вариантов:

- Supabase RPC;
- Supabase Edge Functions;
- SQL-функции + RLS;
- комбинацию Edge Function + транзакционная SQL-функция.

### Требования к backend-операциям

Каждая операция должна:

- быть атомарной;
- валидировать входные данные;
- проверять права;
- возвращать нормализованный ответ;
- быть безопасной к повторному вызову;
- писать аудит в таймлайн или журнал.

### Для создания заказа операция должна делать за один вызов

- создать клиента или выбрать существующего;
- списать кэшбэк, если применён;
- создать заказ;
- создать позиции заказа;
- создать платежи;
- создать начальный таймлайн;
- при необходимости создать уведомления.

### Критерий завершения

Во фронтенде больше нет длинных цепочек из 5-10 последовательных запросов для одной бизнес-операции.

## Этап 5. Нормализовать слой данных

### Цель

Убрать дублирование и хаос в хуках загрузки данных.

### Проблема

Сейчас почти каждый хук вручную реализует:

- `loading`;
- `error`;
- `fetch`;
- `refetch`;
- `useEffect` для начальной загрузки.

### Решение

Перейти на единый data layer. Предпочтительный вариант:

- TanStack Query

### Что это даст

- нормальный кеш;
- инвалидацию после мутаций;
- единообразные ошибки;
- меньше ручного кода;
- проще realtime и optimistic update.

### Какие сущности перевести

- orders
- order detail
- clients
- users
- finance
- notifications
- services
- cancel reasons

### Критерий завершения

Новые экраны и мутации больше не строятся на ручном копировании одного и того же `useEffect + useState`.

## Definition of Done для всего плана

План можно считать выполненным, когда соблюдены все условия:

- `npm run build` зеленый;
- `npm run lint` зеленый;
- тесты есть и проходят;
